## Summary

| Severity  | Count | What they mean |
|-----------|-------|---|
| **Blocker** | **6** | Lose money, leak PII, or break legal compliance |
| **High**   | **13** | Major feature broken, wrong math, perf cliff |
| **Medium** | **14** | Visible bug or convention violation with workaround |
| **Low**    | **7** | Polish, edge case, future-proofing |

The codebase passes the **structural** hunts cleanly — no empty handlers, no division-by-zero, no force-unwraps in user paths, secrets gitignored, sheet/dismiss pairs balanced. The Blockers are the kind of bugs that *only* show up when you stop treating the app as a demo and start trusting it with real money/data — silent-failure swallowing in payment paths, signed-URL persistence regressions, DPDP-Act promises not backed by execution, and floating-point money math.

The silent-failure pattern (50 instances of `try? await … ?? []`) is the **systemic finding** that ties the worst Blockers together.

## Blockers (fix before any real customer ships)

### B1. Payment view silently shows "₹0 received" on fetch failure → owner double-charges the customer
**File:** `Features/Orders/PaymentsSectionView.swift:101`
```swift
} catch { payments = [] }
```
If Supabase is unreachable when the order detail opens, "Received" shows ₹0 and "Balance due" shows the **full order total in orange**. The owner sees this, hits "Record payment" (suggested amount = full balance), and the customer pays a second time. There's no way for the owner to distinguish *"quiet account"* from *"network failure."*

**Fix:** Track `loadError: String?`; show banner *"Couldn't load payment history — retry before recording"* and **disable the Record-payment button** when the load failed.

---

### B2. `DesignTryOn` persists 1-hour signed URLs in the DB → customer photos become unresolvable after an hour
**File:** `Features/Designs/VirtualTryOnView.swift:183-194`, `Models/DesignRender.swift:88-96`
```swift
_ = try await DesignTryOnsService.record(NewDesignTryOn(
    ...
    customer_photo_url: custUpload.immediateURL,   // signed, expires in 1 hr
    result_image_url:   resultUpload.immediateURL,
    ...
))
```
This **regresses the P0-2 fix** that established "persist (bucket, path), regenerate signed URL on read." The earlier fix covered sketches + renders; tryons were missed. `customer-photos` is a private bucket — the signed URL dies after 60 minutes and the customer's VTO becomes unviewable.

**Fix:** Add `customer_photo_path` and `result_image_path` columns to `design_tryons` + `NewDesignTryOn`; persist `.path` instead of `.immediateURL`; regenerate at view time via `StorageService.signedURL(bucket:path:)`.

---

### B3. `DesignRender` still writes `result_image_url` even though the path column was added → stale signed URL persists, confuses readers
**File:** `Features/Designs/RenderView.swift:160-171`
```swift
result_image_url: upload.immediateURL,   // 1-hr signed URL — persisted to DB
result_image_path: upload.path,          // correct
```
P0-2 added `result_image_path` and the model comments say `resultImageUrl` is deprecated, but new records still write to it. Callers fall back to the bad URL if path is nil for any reason. **Fix:** pass `nil` for `result_image_url`.

### B4. VTO consent timestamp captured ~60-90s AFTER actual consent → DPDP audit discrepancy
**File:** `Features/Designs/VirtualTryOnView.swift:183-194`
```swift
let (renderData, _) = try await URLSession.shared.data(from: renderUrl)  // ~30-60s
let result = try await GeminiService.virtualTryOn(...)                    // ~30s
phase = .uploading
let custData = ...
let custUpload = try await StorageService.upload(...)
...
customer_consent_signed_at: ISO8601DateFormatter().string(from: Date()),  // recorded LATE
```
The stored consent timestamp can be 60-120 seconds after the customer actually agreed. Worse, if the Gemini call throws, **no consent record is written at all** even though the customer's biometric data was already passed to a third-party API.

**Fix:** Capture `let consentAt = Date()` immediately after the `guard let cust = customer ...` line (before any network work), then write `Formatters.iso8601.string(from: consentAt)` to the DB. If the upload chain throws, write a "consent given but processing failed" audit row.

### B5. DPDP Act customer-photo retention promised but no deletion job exists
**Files:** UI claim at `Features/Designs/VirtualTryOnView.swift:58, 103`; schema `supabase/migrations/0013_renders_and_tryons.sql:34` has `purge_at` column + index; **`supabase/functions/` directory does not exist**.

```swift
Text("Customer photo auto-deletes after 7 days unless saved to lookbook.")
```
The schema-level work was done (column + index) but nothing actually deletes rows or storage objects when `purge_at < now()`. DPDP Section 6 requires the data controller to implement the deletion right they assert. An auditor would see the UI claim, ask for deletion evidence, and the boutique would fail the audit.

**Fix:** Supabase Edge Function on daily cron — selects `design_tryons where purge_at < now() AND saved_to_lookbook = false`, deletes objects from `customer-photos` and `vto-results` buckets, deletes the row. ~40 lines of TypeScript.

---

### B6. Order create is not atomic → orphan order with no line items + unconverted inquiry on partial failure
**File:** `Services/OrdersService.swift:48-78`
Three sequential round-trips (header insert → items insert → inquiry update) with no transaction. If step 2 throws (duplicate UUID, FK constraint), the order header exists with zero items. If step 3 throws, the order is committed but the inquiry still shows unconverted in the Kanban.

**Fix:** Move to a Postgres RPC function in a single transaction; or as a stopgap, delete the orphaned order in a catch block.

## High

### H1. Dashboard "Today's revenue" shows ₹0 on any network hiccup with no warning
**File:** `Features/Dashboard/DashboardView.swift:270-274, 307, 341, 370` (6 `try? await … ?? []` patterns in one load)
The owner's morning briefing shows: ₹0 revenue, 0 appointments, 0 inquiries, 0 overdue — i.e. *"a totally normal slow day."* If Supabase is down, this is a lie. **Fix:** track `loadFailed`, show "stale data — last refreshed HH:MM" banner.

### H2. Order status updates silently fail → owner re-sends WhatsApp updates already sent
**Files:** `OrderDetailView.swift:255`, `DesignDetailView.swift:44`, `AlterationsSectionView.swift:28`, `CalendarView.swift:50, 77`
`try? await Service.updateStatus(...)` — on failure UI stays on old status. Owner thinks they marked it shipped, re-marks it, re-fires the WhatsApp confirmation. **Fix:** `do/catch` with transient toast.

### H3. `OrderDetailView.advance` doesn't reload child sections
After status change, embedded `PaymentsSectionView`, `AlterationsSectionView`, `OrderTimelineView` keep stale state from initial load. **Fix:** broadcast `.orderDidChange` notification; child views re-fetch.

### H4. No `scenePhase` observer — Dashboard stale on app foreground
Owner closes app at 9 AM, reopens at 2 PM — dashboard hasn't moved. **Fix:** add `@Environment(\.scenePhase)` to AppShellView, post a `.appDidForeground` notification on `.active`, list views re-fetch.

### H5. `DashboardView.filterOverdue` issues 1 query per order — N-way serial waterfall
**File:** `DashboardView.swift:363-380` — 50 open orders = 50 sequential network round-trips on every dashboard load. **Fix:** single grouped query `SELECT order_id, SUM(amount) FROM payments WHERE status='captured' AND order_id IN (...) GROUP BY order_id`.

### H6. Money is `Double` everywhere — rounding drift will accumulate
14+ Double price fields across Order/OrderItem/Payment + GST. Indian GST has half-percent rates with paise rounding. A year of accumulation will produce `₹3,42,150.00000003`-class bugs. **Fix:** `struct Money { let amount: Decimal; let currency: Currency }` with operators.

### H7. Status state machines are advisory, not enforced
`var status` is freely mutable on Order, Inquiry, Design, JobCard, Alteration — any caller can leapfrog `.pending` → `.delivered` without going through `nextOptions`. **Fix:** `private(set) var status` + `transition(to:) throws`.

### H8. Inquiry Kanban has no `nextOptions` guardrails
Unlike Order/Design, Inquiry doesn't declare allowed transitions. Drag-to-any-column is silently destructive — could drag "Delivered" back to "New". **Fix:** add `Inquiry.allowedTransitions`.

### H9. Enums declared but stored as `String` (5+ sites)
`CustomerProfile.stylePersona/bodyType/skinTone/budgetBand`, `DesignLookbook.visibleTo`, `CustomerMeasurement.garmentType`, `JobCard.fabricListJson[].role`, `Order.fulfillmentMethod`. The right enums exist in the same files; storing as string defeats exhaustive switches. **Fix:** use `RawValueOrUnknown<E>` wrapper for forward-compat.

### H10. GST report assumes intra-state → wrong tax for any inter-state order
**File:** `GSTReportExporter.swift:56-57` hardcodes `cgst = gst/2, sgst = gst/2, igst = 0`. When boutique ships to another state, this is wrong — should be IGST 100%. CA files incorrect GSTR-1 → GST mismatch penalty for the boutique. **Fix:** capture `Customer.state` (or per-order shipping_address), compare to `boutique.placeOfSupply`, IGST when different.

### H11. GST CSV export silently produces ₹0 turnover report on fetch failure
**File:** `GSTReportExporter.swift:26, 33` uses `try? await … ?? []`. Owner emails the empty report to their CA. CA files ₹0 turnover. **GST under-filing is a statutory offense.** **Fix:** function should `throws`; caller refuses to export.

### H12. `InvoicePDFGenerator` allocates `NumberFormatter()` without `en_IN` locale → wrong grouping on the legal invoice
**File:** `InvoicePDFGenerator.swift:61-64` — on a device set to `en_US` locale, renders `₹131,250` instead of `₹1,31,250` on a real GST invoice. **Fix:** use `Formatters.inr` / `Formatters.inrPrecise`.

### H13. `OrderItem.gstAmount` semantics ambiguous → invoice line-sum may not match order total
**File:** `OrderCreateView.swift:136-138` stores order-wide GST as the line-item GST. `InvoicePDFGenerator` reverse-engineers the rate from that. Multi-item orders with mixed rates will round inconsistently. **Fix:** store `gst_rate` per line instead of `gst_amount`; reconciliation check before PDF render.

## Medium

### M1. Notification scheduling errors silently swallowed
**File:** `NotificationsService.swift:54, 72` — `add(req) { _ in }` discards the completion error. iOS rate-limits at 64 pending; revoked notification permission also fails silently. Compounded: `refresh()` cancels all reminders before fetching, so one fetch failure wipes the schedule until next launch. **Fix:** log errors, surface a one-time dashboard banner.

### M2. JobCard composer silently falls back to "no measurements / customer = 'Customer'"
**File:** `JobCardComposerView.swift:156-157` — failed measurement fetch → karigar gets a job card with no measurements → wrong garment. Failed customer fetch → PDF prints `customerName ?? "Customer"`. **Fix:** explicit error state; block "Create & open PDF" if either failed.

### M3. Order create's customer picker silently empty on fetch failure → duplicate customer
**File:** `OrderCreateView.swift:105-106` — owner thinks "I haven't added this customer yet" and creates a duplicate.

### M4. `Boutique` query in DashboardView has no boutique_id filter — relies entirely on RLS
**File:** `DashboardView.swift:270` — defense-in-depth violation; data is already in `ctx.boutique`. **Fix:** read from `ctx.boutique` and drop the fetch entirely.

### M5. `important_dates` query has no boutique_id filter (same RLS-only reliance)
**File:** `DashboardView.swift:306-310`. **Fix:** add `.eq("boutique_id", value: bid)`.

### M6. Inquiries Kanban has no loading state
`InquiriesListView.swift` — renders empty briefly during fetch before popping in.

### M7. Date-as-String 8+ times (`dob`, `eventDate`, `dueDate`, `targetDate`, …)
All `String?` with `// YYYY-MM-DD` comments. A `CalendarDate` newtype with custom Codable would prevent the entire format-bug class.

### M8. `CustomerTimelineEvent.Kind` references `SwiftUI.Color` → model knows about UI
**Fix:** move `tint` to a `View+Extensions` mapping; keep model UI-free.

### M9. `CustomerTimelineEvent.id` is fragile string concatenation
Format-dependent equality breaks if any component representation changes. **Fix:** composite hashable struct.

### M10. Unvalidated `Phone` and `GSTIN` types
Phone variants create duplicate "customers" (+919876543210 ≠ 9876543210). GSTIN typos surface at invoice-generation time instead of form submission. **Fix:** validated newtypes.

### M11. VTO uploads happen BEFORE DB consent record → orphan biometric data on DB-insert failure
**File:** `VirtualTryOnView.swift:166-194` — if the DB insert throws, customer photo sits in private bucket with no row, so the purge job can't find it. **Fix:** write DB row first with "uploading" status, then update with paths.

### M12. `AlterationsService.nextRoundNumber` has TOCTOU race
**File:** `AlterationsService.swift:37-39` — fetches max, increments client-side. Two iPads can collide. Same pattern was fixed for order numbers via RPC. **Fix:** add `next_alteration_round(p_order_id uuid)` Postgres function.

### M13. `OrderItem` has no parent reference to `Order`
No structural prevention of mismatched order_id/boutique_id in memory. DB FKs catch it server-side. **Fix:** init-time validation or `OrderItemRef` newtype.

### M14. `New*` mirror types duplicate every entity
Every schema change requires editing two structs. **Fix:** property-wrapper-based encoder strategy.

## Low

### L1. `SignInView.isValidEmail` uses `parts.first!`
Safe in context (guarded by `parts.count == 2`), but fragile under refactor. **Fix:** `parts.first?.isEmpty == false`.

### L2. `OrderDetailView` falls back to hardcoded 5% GST when subtotal is 0
Should use `boutique.defaultGstRate`. **Fix:** add column or constant.

### L3. `Gemini` URLs use `URL(string: ...)!` force-unwrap
**File:** `GeminiService.swift:92, 118`. If `geminiApiKey` is empty or contains a URL-breaking character, crashes mid-render. **Fix:** `guard let url = …`.

### L4. Invoice PDF temp-file write failure silently disables Share button
**File:** `InvoicePreviewView.swift:43` — disk-full scenario fails silently. **Fix:** surface the error.

### L5. Force-unwraps on `Calendar.date(...)!` (6 sites)
DashboardView, CalendarView, ImportantDatesListView — unlikely DST crashes, but no context if they happen. **Fix:** `?? Date()` with logging.

### L6. `InquiriesService.generateInquiryNumber` uses `Int.random` → birthday-paradox collisions at scale
**File:** `InquiriesService.swift:39-44` — ~40% collision probability with 100 inquiries/month. **Fix:** RPC sequence like orders.

### L7. `PaymentsSectionView.balanceDue` not rounded → sub-cent reminder for fully-paid order
Floating-point drift could show WhatsApp "payment reminder" when balance is `₹0.00001`. **Fix:** `.rounded(toPlaces: 2)`.
